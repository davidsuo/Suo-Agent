## 第一部分 · 开发流程契约

### 第一条 · 契约精神

> **改代码前跑一次回归。改完代码再跑一次。全绿才算改完。**

### 第二条 · 三条铁律

**铁律 1**：本地绿、云端绿，代码才可合并
- 任一环境红 → **不允许** merge 到 `main`
- **不允许**"先合并，回头修"

**铁律 2**：不跳过、不忽略、不注释掉失败的测试
- 用例失败先问"系统错了还是脚本错了"
- **断言过时 → 改断言，不删断言**

**铁律 3**：改完必须 commit + push，代码才算"改完"
- `git status` 必须 clean
- **磁盘绿 ≠ 云端绿**

### 第三条 · 提交前必跑清单

```bash
python rag_test/regression/run_all.py           # 本地回归
python rag_test/regression/run_all.py --cloud   # 云端回归
git status                                       # 工作区必须干净

三项全绿，才允许 commit。

### 第四条 · 每次改动的三个动作
改前：跑一次，记录基线

改后：再跑一次，对比结果

全绿：才允许 commit
```

### 第五条 · 例外处理
场景	规则

## 第二部分 · AI 原生设计原则（v2.0 新增）
本节目的：沉淀 2026-10-01 ~ 2026-10-02 Sprint 中形成的"AI 原生"设计共识，避免团队重新踩坑。

### 原则 1：提升 LLM 能力，而不是堆 prompt 规则
反模式：每次遇到新场景，就在 SYSTEM_PROMPT 加一条条件分支。规则越堆越多 → 冲突 → 幻觉。

正模式：改善输入的语义质量（工具返回什么、系统注入什么），让 LLM 自主判断。

判据：加规则前先问——这是"教 LLM 判断"还是"替 LLM 判断"？

案例：US-11 从"加默认顺序规则" → 迭代到"工具资源化交付"。

### 原则 2：工具是"下属交付"，LLM 是"主官统筹"
核心比喻（产品负责人原话）：

告诉 LLM 你需要我做的东西我完成了，现在交给你，接下来就看你 LLM 了！

反模式：工具返回现成成品，LLM 直接抄。

# ❌ 剥夺 LLM 编辑权
return f"图片已生成：![{title}]({url})"

正模式：工具返回资源 + 使用说明，LLM 自己组织。

# ✅ 让 LLM 决定要不要用、放哪里
return (
    f"[图表资源已生成]\n"
    f"- 类型：{chart_type}\n"
    f"- 图片 URL：{chart_url}\n"
    f"- 使用说明：如需在回答中展示这张图，请使用 markdown 图片语法"
    f"引用 ![{title}]({chart_url})。\n"
    f"{summary}"
)

判据：工具返回的是"成品"还是"素材"？成品剥夺编辑权，素材给决策空间。

### 原则 3：不投喂答案，只描述事物本质
反模式（投喂答案）：
例：涉及图表和数据的任务，通常适合 ['图表', '数据', '分析']

→ LLM 会复制样例，不会推理。

正模式（描述本质）：

[说明] 这是本次回答要用的视觉素材，不是回答本身。
→ 让 LLM 自己推理"我是编辑，该怎么用这个素材"。

判据：prompt 里的示例，是"参考格式"还是"标准答案"？前者可以，后者不行。

### 原则 4：让 LLM 用天生擅长的能力
反模式：

自定义占位符（{CHART}）——训练数据里没有

自定义 JSON schema——需要精确记忆

正模式：

真实 markdown：![标题](/charts/xxx.png)

标准 HTTP URL

通用中文自然语言

判据：这个东西，LLM 在训练数据里见过多少次？越多越好。

案例：US-11 放弃 {CHART}，改用真实 markdown 后，LLM 稳定保留。

### 原则 5：后端做"保护 + 兜底"，不做"决策 + 重排"
后端可以做	后端不可以做
URL 安全保护（防 LLM 篡改）	决定图片/表格的位置
LLM 完全失败时兜底	智能重排 tool 消息顺序
输出安全过滤	根据 query 类型改写回答
结构化数据提取	替换 LLM 的表达
判据：这个动作是"保护 LLM 的输出"，还是"替代 LLM 的判断"？

### 原则 6：思考阶段 vs 生成阶段——用对模型
轻量任务（JSON 提取、分类判断）→ deepseek-chat（快、便宜）

生成任务（写报告、多步骤决策）→ deepseek-flash（V4.1 thinking mode）

判据：这个任务需要"先想后说"吗？需要就上 thinking 模型。

案例：US-11 主循环切 deepseek-flash，_analyze_query 保持 deepseek-chat。

### 原则 7：先观察 LLM 的真实行为，再决定动作
反模式：

一看到"随机"就加规则

一看到"丢失"就打补丁

一看到"不符合预期"就改 prompt

正模式：

先加日志，观察 LLM 的固有模式

判断根因是"LLM 能力问题"还是"输入质量问题"

优先解决输入质量，再考虑能力升级

判据：行动基于"观察到的证据"还是"想当然的假设"？

案例：US-11 的 {CHART} 丢失、位置随机，都是通过后端日志观察发现的。

### 原则 8：以客户为中心，不是以 LLM 为中心
产品负责人原话：

我们是以客户为中心还是以 LLM 为中心，你做出的产品最终是让客户用的，不是"我们尊重 LLM 的自主性"。按照这个逻辑，客户是不会用你的产品的。

含义：

"尊重 LLM 的自主性"是手段，不是目的

用户的体验和满意度是最终标准

如果 LLM 的自主行为持续产生差体验，则不是"尊重"，是"能力不足"，需要升级模型或改输入

平衡：

不为了"顺从 LLM"而放弃用户体验

不为了"追求体验"而束缚 LLM

目标是"让 LLM 足够强，输出足够好"

## 第三部分 · 反模式清单（v2.0 新增）
#	反模式	为什么	正确做法
1	每次新场景就加 SYSTEM_PROMPT 规则	规则堆积 → 冲突 → 幻觉	改善输入语义质量
2	工具返回"成品 markdown"	剥夺 LLM 编辑权	返回"素材 + 使用说明"
3	prompt 里投喂具体答案	LLM 只会抄	描述事物本质
4	使用自定义占位符	训练数据里没有	用真实 markdown / URL
5	后端智能重排 tool 消息	替代 LLM 判断	只做保护 + 兜底
6	一遇到问题就换模型	掩盖输入质量问题	先观察，再判断
7	把"尊重 LLM 自主性"当借口	用户体验差	以客户为中心
使用方式：每次设计新功能或改旧功能时，对照本表自检。若发现新反模式，追加到表中并记录到本文档变更日志。

## 第四部分 · 适用范围与演进

### 本契约管什么
流程：改前改后的回归验证、提交规范、违规处理

设计：AI 原生架构决策的原则依据

反模式：已知的坑，避免重踩

### 本契约不管什么
具体业务逻辑（如 RAG 检索算法、前端 UI 细节）

技术选型（如用 ChromaDB 还是其他向量库）

单次迭代的功能决策（这些由用户故事驱动）

### 演进机制
每完成一个里程碑，复盘是否有新原则/新反模式需要沉淀

新增内容 → 追加到第二/三部分 → 更新版本号

已有内容若被推翻 → 不删除，标注"已废弃，见 X.X 条"（保留演进痕迹）
